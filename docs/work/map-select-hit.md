# 맵 선택·칼 판정

담당 세션: `[OnlineSeverGame] 맵 선택·칼 판정 · 01`. 프로토콜 v3 → **v4**.

두 가지를 했다.

1. **칼 판정**: "칼에 맞은 것 같은데 안 맞는다"는 보고를 재현하고 원인을 숫자로 확인한 뒤, 보이는 대로 맞게 고쳤다.
2. **게임 안 맵 선택**: 방장이 다음 맵과 교체 방식을 고른다.

## 1. 어떻게 플레이되는가

### 칼 판정

- 위험물(식칼·고드름·화물 상자·포크)은 이제 **화면에 그린 젤리 몸과 그린 위험물이 겹치면** 맞는다. 머리 장식은 빼고, 엎드리면 낮고 넓게 눌린 몸, 대시 중이면 길쭉한 몸, 밀려나거나 밟혀 납작해지면 그 모양 그대로다.
- 내 캐릭터가 살아 있는 동안 위험물은 **내 캐릭터와 같은 시각**에 그려진다. 예전에는 칼이 내 몸보다 몇 틱 늦게(과거 위치에) 그려져서, 빨리 떨어지는 칼이 실제보다 2~5유닛 위에 보였다. 이제 화면에서 칼끝이 몸에 닿는 순간이 서버가 맞았다고 판정하는 순간이다.
  - 대신 위험물이 생기는 것은 서버가 정하므로(무작위), 예고 표시가 그만큼(같은 PC에서 약 0.2초) 늦게 나타난다. 예고는 1~1.25초라 피할 시간은 충분하다.
  - 다른 플레이어는 여전히 약 0.1초 늦게 그려진다. 다른 사람이 맞는 장면에서는 칼이 먼저 지나가고 그 사람이 조금 뒤에 쓰러져 보일 수 있다(아는 즉시 쓰러지게 해서 차이를 줄였다).
  - 내가 죽으면 위험물이 다른 플레이어와 같은 시각으로 돌아간다. 이때 되감지 않고 0.2초쯤 멈췄다가 이어진다.
- 이동·발판·벽·대시 밀치기·밟기·상자 밀기는 예전과 같은 0.8 × 1.2 상자로 한다(조작감이 바뀌지 않게).

### 맵 선택

- 대기·카운트다운 화면: 왼쪽 접속자 목록에 **★방장** 표시, 그 아래 맵 패널에 "다음 라운드 맵", "교체 방식", "방장" 이름.
- 결과 화면: 순위 아래에 같은 맵 패널.
- 관전 중: 위쪽 안내 아래에 "다음 맵: … (교체 방식)".
- **방장**만 패널에 버튼이 보인다: `1 주방` `2 겨울 처마` `3 창고` `4 디저트 가게`(다음 맵), `순환` `무작위` `고정`(교체 방식). 지금 값은 노란색.
  - 키보드: `1`~`4` 다음 맵, `R` 교체 방식 바꾸기(순환 → 무작위 → 고정 → 순환). 접속 중이면 어느 화면에서나 된다(진행 중에도 눌러 둘 수 있다).
- 방장 = 지금 접속한 사람 중 **가장 먼저 들어온 사람**. 방장이 나가면 그다음에 들어온 사람이 된다.
- 바꾼 맵은 **다음 라운드부터** 쓰인다. 카운트다운이 이미 시작된 라운드도 그대로 진행된다.
  - 방장이 맵을 고르면 "(방장 지정)"이 붙고, 그 라운드가 끝나면 교체 방식대로 그 맵에서 이어진다(순환 중 창고를 고르면 창고 → 디저트 → 주방 …).
  - 무작위는 직전 맵을 빼고 뽑으며, 라운드가 시작될 때 미리 뽑아 둔 값이 대기·결과 화면에 보인다.
  - 고정은 같은 맵을 계속한다. 고정 중에 다른 맵을 고르면 그 맵으로 고정된다.
- 서버 실행 옵션(`--maps cycle|random`, `--map N`)은 서버를 켰을 때의 시작값이다.

## 2. 원인 확인 (재현과 숫자)

### 2.1 그림과 판정의 폭 차이

스프라이트를 직접 쟀다(알파 128 이상 = 외곽선 포함, 피벗 기준, 0.1유닛 높이 띠마다 좌우 끝).

| 대상 | 그림 | 예전 판정 |
|---|---|---|
| 젤리 몸(대기, 장식 제외) | 배 부분(0.2~0.8) 반폭 0.51, 발 0.39, 머리 위쪽 0.26, 키 1.2 | 0.8 × 1.2 상자(반폭 0.4) |
| 식칼 | 칼날 반폭 0.12~0.13, 손잡이 0.09, 높이 1.0 | 반폭 0.2 × 1.0 |
| 고드름 | 끝 0.03 → 위 0.22로 넓어짐, 높이 1.24 | 반폭 0.2 × 1.2 |
| 화물 상자 | 반폭 0.71, 높이 1.21 | 0.7 × 1.2 |
| 포크 | 갈래 반폭 0.19, 손잡이 0.06~0.09, 높이 1.2 | 0.25 × 1.2 |

조율 세션의 단서 (1) "젤리 그림이 0.1씩 넓다"는 맞았다. 단서 (2) "칼 그림 폭 0.5"는 그림 파일(64 px = 0.5유닛) 크기였고, 실제 칼날은 0.24로 판정(0.4)보다 **좁다**. 그래서 식칼은 두 차이가 거의 상쇄되어, 칼 가운데와 몸 가운데 거리로 따지면 그림이 닿는 거리 0.62~0.64 대 예전 판정 0.6이다. 폭 차이가 큰 것은 고드름(0.66 대 0.6, 대신 머리 쪽은 좁음)·화물 상자(1.23 대 1.1)·포크(0.70 대 0.65)였다.

서버 + 봇 8(시드 5, 4맵 순환, 같은 봇 프로그램)으로 예전 판정과 그림 판정을 같은 틱에 둘 다 재서 비교했다(`--legacy-hitbox`, 라운드 끝 `hit rule …` 로그).

(표는 3.1)

### 2.2 그리는 시각 차이 (주원인)

- 내 캐릭터 = 예측: 서버 틱 `최신 스냅샷 + 미확인 입력 수`의 위치를 그린다.
- 위험물(예전) = 보간: `최신 스냅샷 - 2틱` 근처를 그린다.
- 같은 PC 접속에서도 미확인 입력이 4~5개였다(서버 입력 큐에 입력이 몇 개씩 쌓여 기다림). 그래서 같은 화면에서 칼은 내 몸보다 약 6~7틱(0.3초) 과거였다. 식칼은 틱당 0.7, 고드름은 최대 1.0 떨어지므로 **칼이 실제보다 수 유닛 위에** 보였다.
  - "보였는데 안 맞음": 실제 칼은 이미 바닥에 꽂혔는데 화면의 칼은 아직 내 몸을 지나가는 중.
  - "안 보였는데 맞음": 화면의 칼은 아직 머리 위인데 실제 칼은 이미 몸에 닿음.
- 클라이언트가 같은 프레임에 그린 칼과 몸을 그림 모양으로 겹쳐 보고 서버 판정(내 사망)과 맞춰 세었다(`HitViewStats`, 라운드 끝 `[Net] round N hitview …` 로그). 예전 방식(보간 시각)과 새 방식(예측 시각)을 한 실행에서 같이 잰다.

(표는 3.2)

## 3. 전후 비교

### 3.1 서버 + 봇 8 (판정 모양)

같은 봇 프로그램(바꾸기 전 봇), 시드 5, 4맵 순환, 라운드마다 7명 사망. "닿음"은 그 틱에 다른 규칙으로 겹쳤는지.

| 판정 | 사망 | 사망 중 다른 규칙으로는 안 닿음 | 다른 규칙이면 죽었을 생존 | 0.1유닛 안 스침 |
|---|---|---|---|---|
| 예전 상자(`--legacy-hitbox`) | 28 | 3 (그림은 안 닿았는데 죽음) | 7 (그림은 겹쳤는데 살아남음) | 1 |
| 그림 모양(지금) | 28 | 9 (예전 상자였으면 그 틱엔 안 죽음) | 3 (예전 상자였으면 죽음: 머리 모서리 등) | 5 |

- 예전 판정에서 그림과 어긋난 경우: 맵별로 주방 1·1, 겨울 1·0, 창고 0·2, 디저트 1·4(사망·생존). 생존 쪽은 대부분 그림이 0.01~0.07유닛 겹친 것(화물 상자·포크처럼 그림이 판정보다 넓은 것)과, 대시·밀려남 자세(그림이 0.24~0.26유닛 겹침)였다.
- 봇은 위험 구간에 여유 0.3을 두고 피해서 가장자리 스침이 드물다. 사람은 더 바짝 피하므로 차이를 더 자주 본다.
- 로그: `side-session-notes/.../map-select-hit-01/logs/server-legacy.log`, `server-visual.log`.

### 3.2 클라이언트 화면 (그리는 시각)

Unity 클라이언트 1(자동 입력 `-autoplay`, 방장) + 봇 3, 같은 PC, 핑 16~17 ms. 10라운드(4맵 모두), 내 캐릭터 10번 사망. 한 실행에서 두 그리기 방식을 동시에 쟀다.

| | 예전(보간 시각) | 지금(예측 시각) |
|---|---|---|
| 죽었는데 직전 0.5초 안에 화면에서 닿은 위험물이 없음 | **8 / 10** | **0 / 10** |
| 화면에서 닿았는데 그 위험물에 안 죽음 | 2 | 0 |
| 내 몸과 위험물의 시간 차(라운드 평균) | 5.2~6.0틱 | 0(같은 틱) |
| 떨어지는 위험물의 두 방식 위치 차 | 평균 3.1~4.2유닛, 최대 5.9유닛 | — |

- 시간 차가 큰 이유: 같은 PC인데도 미확인 입력이 4~5개였다. 서버 입력 큐에 입력이 몇 개씩 쌓여 차례를 기다린다(클라이언트가 프레임이 늦을 때 몇 틱을 한꺼번에 보내면 큐가 늘고, 서버는 틱마다 하나만 꺼내므로 줄지 않는다). 그래서 칼이 몸보다 0.3초쯤 과거로 그려졌다. 단서 (3)이 주원인이었다.
- 새 방식에서 예고가 늦게 보이는 만큼(약 5틱) 실제로 피할 수 있는 시간이 줄어든 것은 아니다. 예전에도 예고의 마지막 5틱에 누른 입력은 칼이 떨어진 뒤에 서버에 도착했다. 이제 화면이 그 사실대로 보인다. 입력 큐 대기 자체를 줄이는 것은 별도 작업 후보(6장).
- 닿는 순간 스크린샷(`-touchshot`, 지금 방식에서 처음 닿아 보인 프레임): 식칼·고드름·포크 모두 칼끝이 머리 외곽선에 막 닿은 장면이고, 그 위험물에 서버가 사망 판정(`death #1 'Me' by knife#37 … drawn-shape gap -0.14 u`). `side-session-notes/.../map-select-hit-01/shots/touch_*.png`.

## 4. 어떻게 구현했는가

### 판정 모양 (`Shared/Simulation/HitShapes.cs`)

- `HitBand(Bottom, Top, Left, Right)`: 기준점(플레이어 발 가운데, 위험물 끝)에서 잰 가로 띠 하나. 오른쪽을 볼 때 기준이고 왼쪽을 보면 뒤집는다.
- 몸 `Body`, 대시 `Dash`, 밀려남 `Stunned`는 시트를 잰 값. 엎드림 `Crouch` = `Body` × (1.15, 0.6), 밟힘 `Stomped` = `Stunned` × (1.35, 0.4). 이 배율은 `PlayerView`가 스프라이트를 누르는 값과 같다(바꾸면 둘 다 바꿀 것).
- 몸 띠는 8색 중 가장 좁은 값(장식은 픽셀을 더하기만 하므로 장식이 빠진다), 동작은 그 동작의 모든 프레임을 합친 값.
- 달리기·점프·낙하 프레임은 대기 몸과 0.06 이내라 대기 몸을 쓴다.
- `OfPlayer(state)`: 스턴(밟힘이면 납작) → 대시 → 엎드림 → 몸. `PlayerView.PickAnimation`과 같은 우선순위.
- `Separation(player, kind, x, fromTipY, toTipY)`: 위험물 띠마다 이번 틱 낙하 전체(이전 끝 ~ 새 끝)를 쓴 영역과 몸 띠의 거리 중 가장 작은 값. 음수면 겹침. 끝이 닿기만 하면(0) 맞지 않는다. `Hits` = 음수.
- `LegacySeparation`: 예전 규칙(종류별 폭 상자 vs 0.8 × 1.2) — 비교 로그용.
- 정수만 쓴다(서버·클라이언트 같은 결과).
- 착지·쌓임·예고 기둥·상자 크기는 그대로 `HazardSpec` 폭이다. 칼이 발판 끝에 걸리는지는 이번 범위가 아니다.

### 서버

- `GameRoom.StepKnives`: 위험물 한 틱 전 끝 높이(`fromY`)와 새 끝으로 `HitShapes.Separation`. `RoomConfig.LegacyHitbox`(`--legacy-hitbox`)면 예전 규칙으로 판정.
- `HitStats`: 두 규칙을 매 틱 같이 재서 라운드 끝에 `hit rule …: deaths D (not touching under <다른 규칙>: a), survivors <다른 규칙> would have killed: b, near misses (< 0.1 u): c`. `--verbose`면 하나씩(`spared …`, `near …`). 사망 로그에 두 규칙의 거리.
- 봇(`DodgeBrain`): 위험 구간 = 그림 위험물 반폭 + 그림 몸 반폭 0.51 + 여유 0.3.

### 클라이언트 (`NetworkSession`)

- `HazardTargetTick()`: 예측 중이고 Playing이면 `최신 스냅샷 틱 + 미확인 입력 수 - 1 + (틱 사이 진행률)` = 내 화면 몸과 같은 서버 틱. 아니면 보간 시각.
- `AdvanceHazardClock`: 목표를 실시간 속도로 따라가고, 작은 어긋남은 속도(0~3배)로 흡수, 뒤로 가야 하면 멈춤, 8틱 넘게 어긋나면 바로 옮김.
- `CollectHazards(tick)`: 최신 스냅샷 이전이면 스냅샷 보간, 이후면 최신 스냅샷의 위험물을 `KnifePhysics.Step`으로 앞서 계산(그 틱의 녹는 발판 모양, 최신 상자). 앞서 계산한 화물이 착지하면 금 간 그림 대신 상자 그림(`SwordRender.AsBox`), 최신 스냅샷에 새로 생긴 상자는 보간을 기다리지 않고 바로 그린다(사이에 상자가 비어 보이지 않게).
- 위험물이 앞서 그려지는 동안 다른 플레이어의 탈락은 최신 스냅샷 기준으로 바로 보인다.
- `HitViewStats`: 진단(2.2).

### 맵 선택 (프로토콜 v4)

- 새 패킷: `RoomInfo`(32, S: 방장 id, 다음 맵, 교체 방식, 방장 지정 여부), `MapRequest`(50, C: 맵 0 = 그대로, 방식 0 = 그대로). 자세한 바이트와 규칙은 `docs/protocol.md` 3장, 5장 '맵 교체'.
- `MapRotation` 열거형을 Shared(`PacketType.cs`)로 옮겼다(값 1 순환, 2 무작위, 3 고정).
- `GameRoom`:
  - `RoomPlayer.JoinOrder`(들어온 순서). `HostId` = 남은 사람 중 가장 작은 순서. id는 빈 번호를 다시 쓰므로 id로 정하지 않는다.
  - `_nextStage`(다음 새 카운트다운의 맵), `_nextChosen`(방장 지정), `_mapPlayed`. 카운트다운 시작에 `_stage = _nextStage`, Playing 시작에 방장 지정이 없으면 `_nextStage = MapAfter(_stage)`(순환 다음 / 무작위 / 같은 맵). 취소된 카운트다운은 Playing에 가지 않았으므로 같은 맵.
  - `RequestMap(playerId, stageId, rotation)`: 방장 아니면·없는 맵·잘못된 방식이면 무시하고 로그. 받아들이면 로그.
  - `RoomInfo`는 새로 온 사람에게 바로, 모두에게는 값이 바뀐 틱 끝(스냅샷 앞)에 한 번.
- `Connection` → `NetEventKind.MapRequest` → `GameServer`가 그 연결의 플레이어로 `RequestMap`.
- 클라이언트: `SessionState`(HostId, NextMapId/Name, Rotation, NextChosen, IsHost), `IGameSession.RequestMap`, `GameUI.DrawMapChoice`·`HandleMapKeys`. 버튼·키는 요청만 보내고 화면 값은 서버의 `RoomInfo`로 바뀐다.

### 새 위험물에 적용할 원칙 (옆 칼 등 다음 작업용)

1. **맞는 모양 = 그린 모양.** 새 위험물은 스프라이트를 같은 방법(알파 128, 0.1유닛 띠, 10 단위 올림)으로 재서 `HitShapes`에 띠 목록을 넣는다. 플레이어 쪽은 `HitShapes.OfPlayer`(자세별)를 그대로 쓴다. 이동 상자(`PlayerState.Bounds`)로 위험물을 판정하지 않는다.
2. **지나간 영역 전체.** 한 틱에 움직인 거리 전체를 쓸어 터널링을 막는다. 지금 `Separation`은 세로 낙하(끝 높이 from→to)만 받는다. 가로로 나는 위험물은 x 이전→새 위치를 쓰는 판(예: `SeparationSwept(player, bands, x0, y0, x1, y1)`)을 추가해 같은 띠 비교를 쓰면 된다.
3. **결정적이면 내 예측 시각에 그린다.** 움직임이 서버 무작위 없이 정해지는 위험물은 `NetworkSession.CollectHazards`처럼 최신 스냅샷에서 Shared 물리로 앞서 계산해 그린다. 스냅샷 보간 시각에 그리면 빠른 위험물일수록 화면과 판정이 어긋난다.
4. 서버 로그에 두 규칙/거리(가장 가까운 거리, near miss)를 남겨 사람이 숫자로 확인할 수 있게 한다.

### 확인 못 한 것 / 사람이 직접 해 볼 것

- **버튼 클릭**: 자동 시험에서 창에 보낸 마우스 메시지는 Unity IMGUI가 받지 않아(실제 커서 위치를 읽음) 키로만 확인했다. 버튼은 키와 같은 `RequestMap`을 부른다. 직접 눌러 보기.
- 사람 손으로 플레이했을 때 "보이는 대로 맞는지" 느낌, 특히 가장자리 스침·엎드려 피하기·대시 중 맞기(대시 그림이 길어 예전보다 잘 맞는다).
- 예고가 약 0.25초 늦게 나타나는 것이 거슬리는지.
- 다른 사람이 맞는 장면: 칼은 내 시각, 다른 사람은 0.1초 과거라 칼이 먼저 지나가고 조금 뒤 쓰러져 보일 수 있다.
- 실제 네트워크 지연(다른 PC·인터넷)에서의 모습. 지연이 크면 예고가 그만큼 더 늦게 보인다.
- 방장이 아닌 두 번째 사람 화면(버튼 없음, 방장 이름 표시)은 봇으로만 대신했다(봇은 화면이 없음).

### 남은 일 후보

- **입력 큐 대기 줄이기**(서버): 같은 PC에서도 입력이 4~5틱(0.2초 이상) 큐에서 기다린다. 큐가 계속 2개 넘게 차 있으면 조금씩 덜어 내는 식의 조정이 필요해 보인다. 반응 속도·예고 시간에 직접 영향.
- 칼이 발판 끝에 걸리는 폭(`HazardSpec.Width`)은 그대로 두었다. 그림 칼끝이 발판 밖인데 발판에 꽂히는 경우가 있을 수 있다.
- 대기 화면 위쪽 띠 문구가 길어 잘린다(예전부터, 맵 이름이 길면 더).
