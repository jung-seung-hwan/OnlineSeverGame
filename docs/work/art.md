## 1. 어떻게 보이게 되는가

확정된 아트 방향(2026-10-27): **주방 젤리 생존**. 손바닥만 한 젤리·떡 생물 8마리가 밤의 거대한 주방, 도마 위에서 떨어지는 식칼을 피한다.

- 캐릭터: 둥근 젤리 덩어리 하나(세로:가로 3:2), 큰 세로 타원 눈, 팔 없음·짧은 발 두 개. 같은 모델에 몸 색 8가지 + 머리 장식 8가지. 장식은 색이 아니라 모양으로 구별된다(색약 대비).
- 동작 8종: 대기·달리기·점프 상승·낙하·대시·밀려남·사망·승리. 늘어나고 찌그러지는 것이 주된 표현. 좌우는 뒤집기.
- 첫 맵: 바닥 = 두꺼운 원목 도마, 양쪽 낮은 발판 = 벽 선반, 가운데 높은 발판 = 체인에 매단 뒤집힌 냄비 뚜껑.
- 위험물: 칼끝이 아래인 식칼. 1초 전에 빨간 반투명 그림자 기둥 + 착지 표시로 예고.
- 화면 대비: 배경은 어둡고 저채도, 발판·바닥 윗면에 밝은 선, 캐릭터는 중간 밝기의 선명한 색, 칼과 빨간 예고만 최고 대비.

## 3. 어떻게 만들었는가

### 기준 프롬프트 v1 (개인 파일, Git 제외)

위치: `.vibe-local/prompts/` (README.md, style_v1.md, character-sheet_v1.md, pose-sheet_v1.md, map-kitchen_v1.md, knife-warning_v1.md, build.sh). 각 파일에 고정 요소 / 바꿀 수 있는 입력 / 영문 브리프가 나뉘어 있고 버전·날짜가 적혀 있다.

공통 고정 요소(style_v1)에서 정한 것과 이유:
- **만화풍 3D 느낌**: 최종 스프라이트가 Blender 툰 셰이딩 렌더라서 콘셉트도 "단순 3D 모델 + 셀 셰이딩 2~3단 + 고른 외곽선"으로 그리게 했다. 손그림 붓질은 모델로 옮길 수 없다.
- **옆면 시점 해석**: 카메라는 놀이 평면에 수직인 직교 카메라(원근·위아래 각도 없음). 캐릭터는 진행 방향을 보되 얼굴만 관객 쪽으로 살짝 돌려 두 눈이 보이게 했다. 완전한 옆모습(눈 하나)은 젤리 얼굴의 표정이 읽히지 않는다. Blender에서는 모델을 진행 방향에서 카메라 쪽으로 30° 정도 돌려 렌더하면 된다.
- **몸 비율 3:2**: 서버 충돌 상자 0.8 × 1.2 유닛(`Shared/Simulation/GameConstants.cs`)을 실루엣이 채우도록.
- **64픽셀 높이에서 읽히는 실루엣**: 8명이 24유닛 폭 화면에 있으면 캐릭터는 화면 높이의 약 9%라서 잔무늬는 의미가 없다.
- **시트 배경 #2B2E36 단색**: 게임 배경과 비슷한 어두운 저채도라서 실제 대비로 판단할 수 있다.

### 맵 구도는 스테이지 좌표에서 계산

`Shared/Simulation/Stage.cs` `Stage.Default`: 가로 0~24, 보이는 높이 13.5, 발판 3개(x 3~9·15~21 윗면 2.4, x 9~15 윗면 4.8). 클라이언트 카메라는 바닥 아래 약 1.1유닛까지 보여 준다. 이미지 전체 = 놀이 영역으로 잡아 다음 위치를 프롬프트에 숫자로 넣었다.

| 면 | 아래에서 높이 | 가로 범위 |
|---|---|---|
| 도마(바닥) 윗면 | 8% | 0~100% |
| 왼쪽 선반 윗면 | 26% | 12.5~37.5% |
| 오른쪽 선반 윗면 | 26% | 62.5~87.5% |
| 냄비 뚜껑 윗면 | 44% | 37.5~62.5% |

발판은 아래에서 통과하는 한 방향 발판이라 발판 아래를 비워 두게 했다(기둥·냄비 금지). 위쪽 절반은 칼이 떨어지는 곳이라 차분하게, 빨강·순백은 칼과 예고용으로 남겨 두게 했다.

### 생성

`codex exec --skip-git-repo-check -C D:/OnlineSeverGame - < 프롬프트.txt`로 용도마다 1장씩 생성(image_generation 기능). 결과는 `~/.codex/generated_images/<스레드>/`에서 `Art/concept/<용도>_v<버전>_<번호>.png`로 복사했다.

1차(v1) 4장 중 캐릭터 2장은 몸 비율, 맵은 세로 배치가 기준과 달라 원인을 찾아 기준을 고쳤다(v2). 같은 프롬프트로 다시 뽑지 않았다.
- **style v2**: 몸 문장의 "gumdrop / mochi"가 납작한 모양을 끌어오고 "3:2"가 무시돼서, "세로로 선 달걀, 120 × 80 픽셀처럼, 기본 자세에서 가로가 세로보다 넓으면 안 됨"으로 바꿨다. 나머지 고정 블록은 그대로.
- **map v2**: "두꺼운 도마, 앞면을 보여라"가 도마를 화면 아래 1/5로 키웠다. 도마를 얇은 띠로, 높이를 캐릭터 키 단위(선반 = 캐릭터 2개, 뚜껑 = 4개 위)로도 적고, 원경 가로 선반을 금지했다.

## 6. Blender 모델과 스프라이트 (아트 · 02)

### 6.1 어떻게 보이는가

- 캐릭터: 세로로 선 통통한 달걀 몸 하나(그림은 폭 1.0 × 키 1.2로 판정 0.8 × 1.2보다 좌우로 0.1씩 넓다. 6.3 참고), 큰 세로 타원 눈 + 반짝임 두 점, 작은 입, 짧은 발 두 개. 진행 방향(오른쪽)에서 카메라 쪽으로 30° 돌린 시점이라 두 눈이 몸 오른쪽에 보인다. 셀 셰이딩 3단(그림자 / 중간 / 밝음) + 왼쪽 위 작은 광택점 + 밝은 테두리 빛 + 짙은 외곽선. 몸 색 8가지는 1장 표의 값 그대로, 장식 8종은 모양으로 구별.
- 동작 8종(표정도 동작마다 바뀜):

### 6.3 어떻게 만들었는가

모델·장면·렌더·시트 합치기를 Blender 파이썬 스크립트 하나(`Art/blender/build_sprites.py`)로 한다. 손으로 만진 Blender 파일이 아니라 스크립트가 기준이라, 색·크기·포즈를 숫자로 고치고 다시 돌리면 같은 결과가 나온다. `.blend` 파일 3개는 스크립트가 만든 장면을 열어 보기 위한 것이다.

- 좌표: 월드 X = 게임 x, 월드 Z = 게임 y. 카메라는 직교, +Y 방향을 바라봄(옆면, 위아래 각도 없음). 렌더 영역과 해상도를 "픽셀/유닛"으로 정해 스프라이트 크기가 게임 단위와 정확히 맞는다.
- 몸: 회전체 메시. 반지름 0.48(외곽선 포함 폭 1.0), 아래는 모서리가 둥근 평평한 바닥, 위는 살짝 좁아지는 둥근 머리. 몸 바닥 0.07~꼭대기 1.19, 발이 0~0.13을 채운다. 위에서 보면 원이라 30° 돌려도 화면 폭이 그대로다.
  - **기준 변경 (2026-10-27, 사용자 요청)**: 처음에는 반지름 0.39로 판정 0.8 × 1.2를 꼭 맞게 채웠는데(세로:가로 3:2, 콘셉트 style v2 기준), 게임 화면에서 "너무 얄쌍해서 통통함이 반감된다"는 사용자 의견으로 0.39 / 0.44 / 0.48을 판정 상자와 겹쳐 비교했고 사용자가 0.48을 골랐다. 이제 그림(세로:가로 약 1.25)이 판정보다 좌우로 약 0.1씩 넓다. **판정은 그대로**(Shared·서버 변경 없음). 그림이 판정보다 넓으면 칼이 몸 가장자리를 스쳐 보여도 죽지 않는 쪽이라 억울함은 적다. 시험용으로 환경 변수 `JELLY_BODY_R`로 반지름을 바꿔 렌더할 수 있다. 발 위치는 반지름에 비례해 따라가고, 눈·입은 몸 표면에서 계산하므로 같이 따라온다.
- 동작(셰이프 키): 몸·발·눈·입을 래티스(3 × 2 × 4 점, 선형 보간) 하나로 변형한다. 래티스에 셰이프 키 6개(`tall` 늘이기, `flat` 납작, `lean` 기울이기, `long` 대시 길이, `taper` 뒤를 낮춤, `puddle` 웅덩이)를 두고 프레임마다 값을 섞는다. 바닥 줄은 거의 움직이지 않아 발이 땅에 붙어 있다. 넘어짐·깡충은 몸 전체를 담은 빈 객체(`Pose`)의 회전·높이로 한다.
- 장식은 변형하지 않는다(리본·왕관이 몸과 같이 찌그러지면 모양 구별이 흐려진다). 대신 프레임마다 변형된 몸의 가장 높은 점을 재서 장식 기준점(`DecorAnchor`)을 거기 올리고 동작별 기울기를 준다. 사망 마지막 두 프레임은 장식을 떼어 웅덩이 위로 떨어뜨린다.
- 얼굴: 표정마다 객체 하나(눈: 보통·크게·찌푸림·웃음·X·소용돌이, 입: 미소·찡그림·o·벌림)를 몸 표면에 붙여 두고 프레임마다 하나씩만 보이게 한다. 눈은 로컬 방위 −47°·−13°(카메라 쪽이 −60°), 높이 0.68.
- 툰 셰이딩: EEVEE의 Shader to RGB로 빛 세기를 받아 계단 램프(그림자 / 중간 / 밝음)로 몸 색과 그림자 색을 섞고, 광택(Glossy)은 높은 문턱으로 잘라 흰 점 하나만, 가장자리 빛(Layer Weight)은 밝은 색 띠로 더한다. 결과를 Emission으로 내보내고 색 관리를 Standard로 해서 렌더 색 = 지정한 색(#E2475A 등). 그림자 색은 몸 색을 어둡게 하고 보랏빛을 섞었다. 빛은 왼쪽 위 앞의 태양 하나, 그림자 드리우기 없음(장식 그림자가 얼굴에 지저분하게 떨어지지 않게).
- 외곽선: 뒤집은 껍데기(Solidify 바깥 0.02유닛 ≈ 2.5픽셀, 법선 뒤집기 + 뒷면 숨김). 몸 외곽선은 몸 색을 아주 어둡게 한 색, 장식 #1E1A28, 칼 #14161D, 발판 #121318. 배경에는 외곽선을 넣지 않아 뒤로 물러나 보이게 했다.
- 렌더: EEVEE, 투명 배경 RGBA PNG, 샘플 16. 프레임마다 렌더해 numpy로 시트에 붙인다. 그림이 프레임 가장자리에 닿으면 "잘림"으로 보고한다.
- 맵: 벽 타일(Brick 텍스처, 1유닛 칸)·나무결(Wave)·도마 판자(Brick 세로줄)는 절차 텍스처, 빛 무리는 거리 기반 3단 계단. 뚜껑만 툰 셰이딩(둥근 면), 나머지는 평면 색. 발판은 `Stage.Default` 숫자를 스크립트에 그대로 적어 만들었다(바닥 윗면 0, 선반 x 3~9·15~21 윗면 2.4, 뚜껑 x 9~15 윗면 4.8). 발판을 따로 렌더해서 Unity에서 판정 위치에 정확히 놓을 수 있다.

콘셉트와 다르게 정한 것과 이유:
- **3번 왕관을 키웠다**(지름 0.31, 뾰족 끝 높이 0.21, 끝마다 구슬). 콘셉트 평가의 "왕관이 작다"를 반영.
- **광택은 작은 흰 점**. 콘셉트의 크고 부드러운 반사는 툰 계단으로 옮기면 큰 흰 덩어리가 되어 흰 장식·칼날과 겹쳐 보였다(첫 시험 렌더에서 확인).
- **반짝이·먼지·속도선은 넣지 않았다**. 스프라이트에는 캐릭터만 담고 효과는 Unity에서 그리는 편이 뒤집기·색 바꾸기가 쉽다(클라이언트에 대시 잔상이 이미 있음).
- 사망 때 장식은 콘셉트처럼 웅덩이 옆 바닥이 아니라 웅덩이 위에 비스듬히 얹힌다. 30° 돌린 시점에서 옆 바닥에 두면 웅덩이에 가리거나 프레임 밖으로 나갔다.

확인 안 한 것(6.6의 Unity 실행으로 일부 확인함):
- 움직이는 화면에서 흰 장식 vs 칼, 예고 기둥 안에 선 1번 캐릭터를 사람이 눈으로 본 판단. 6.6의 자동 플레이 스크린샷에서는 헷갈리는 장면이 없었지만 사람이 직접 해 보지는 않았다.
- 좌우 뒤집기: 뒤집으면 광택점이 오른쪽 위로 간다(빛 방향도 뒤집힘). 스크린샷에서 거슬리지 않았지만 사람 판단은 아직.
- 16:9보다 넓은 화면: 클라이언트 카메라가 세로 기준이라 21:9에서는 가로 약 34유닛이 보이는데 배경 그림은 27유닛만 덮는다(바깥은 어두운 단색).
- 색약 시뮬레이션은 이번에도 하지 않았다(흑백 구별만).

### 6.6 Unity 클라이언트에 적용 (2026-10-27, 사용자 승인)

사용자가 "임시 도형을 Art/sprites로 교체"를 승인해 이 세션이 `Client/`를 고쳤다(평소 `Client/` 담당은 Unity 클라이언트 세션, 그 세션은 쉬는 중이었고 미커밋 변경 없음을 확인함).

어떻게 보이는가: 접속·미리보기 모두 주방 배경 + 도마 바닥 + 선반 2 + 냄비 뚜껑 위에 젤리 8명이 동작대로 움직인다. 칼은 칼 그림, 예고 기둥·바닥 표시·위쪽 마름모는 전처럼 Unity가 그린다. 내 캐릭터 표시는 UI 이름표의 ▼(따로 표시 없음). 죽은 캐릭터는 사망 동작 후 웅덩이로 남고 조금 어둡다. 공중에서 죽어도 웅덩이와 이름표는 아래 바닥·발판 위에 그린다(서버는 죽은 위치에 멈춰 두므로 그리기에서만 내림). 라운드 도중 들어온 관전자는 대기 모습으로 흐리게. 결과 화면의 승자는 승리 동작(깡충). 벽 바깥(x < 0, x > 24)은 그림 위에 반투명 검정을 덮어 벽 위치를 보여 준다.

구현:
- 그림 복사본: `Client/Assets/Resources/Art/`(characters 8장 + `jelly_sheet.json`, knife, map 조각 4장). 원본은 `Art/sprites/`. 다시 렌더한 뒤에는 아래 명령으로 다시 복사하고 클라이언트를 다시 빌드한다.
- `Client/Assets/Editor/ArtImporter.cs`: 이 폴더 그림의 가져오기 설정(스프라이트, 압축·밉맵 없음, 2의 거듭제곱으로 늘리지 않음, 최대 2048).
- `Client/Assets/Scripts/View/ArtSprites.cs`: 실행 중에 텍스처를 불러 `jelly_sheet.json` 규칙대로 프레임을 자르고(피벗 = 몸 아래 가운데), 칼(피벗 = 칼끝), 맵 조각(map.json의 world_rect)을 스프라이트로 만든다. Unity 쪽 자르기 설정을 따로 둘 필요가 없다.
- `PlayerView`: 동작 고르기 = 관전자 → 대기, 사망 → death, 승자 → victory, 밀려남 → knockback, 대시 → dash, 공중 → 위로 가면 jump 아니면 fall, 가로로 움직이면 run, 아니면 idle. 동작이 바뀌면 처음 프레임부터, 반복 안 하는 동작은 마지막 프레임에서 멈춤. 왼쪽을 보면 `flipX`. 대시 잔상은 같은 프레임을 반투명으로 뒤에.
- `PlayerRender`에 동작용 값 추가(Grounded, VelocityY, Moving, Stunned, Winner, Spectator). 접속 세션은 스냅샷(내 캐릭터는 예측 상태)의 `Grounded`·`Vy`·`Vx`·`StunTicks`에서, 미리보기 세션은 흉내 물리에서 채운다(미리보기 밀치기에 0.3초 밀려남 추가).
- `SwordView`: 칼날·가드·손잡이 사각형 → 칼 스프라이트 하나. `StageView`: 색 사각형 → 맵 조각. 가장 높은 발판 = 냄비 뚜껑, 나머지 = 선반.
- 판정·서버·Shared는 바꾸지 않았다.

다시 복사·빌드(저장소 루트):

```bash
cp Art/sprites/characters/*.png Art/sprites/characters/jelly_sheet.json Client/Assets/Resources/Art/characters/ && cp Art/sprites/knife/knife.png Client/Assets/Resources/Art/knife/ && cp Art/sprites/map/kitchen_bg.png Art/sprites/map/floor_board.png Art/sprites/map/shelf.png Art/sprites/map/pot_lid.png Client/Assets/Resources/Art/map/
```

빌드는 `docs/work/unity-client.md`의 배치 모드 명령 그대로.

실제 확인(Windows 빌드, 자동 입력. 스크린샷·로그는 `.lean/sprite-test/`, Git 제외):
- 배치 모드 빌드 성공, 컴파일 오류·경고 없음. 텍스처 가져오기 설정이 적용됨(.meta: 스프라이트, 압축 없음, 밉맵 없음).
- 오프라인 미리보기(`-preview -autoplay`): 배경·발판 위치가 판정과 맞고(캐릭터 발이 선반·뚜껑 윗면에 닿음), 달리기·점프·낙하·대시·사망 웅덩이, 왼쪽 볼 때 뒤집기 확인. 예외 없음.
- 서버 + 봇 7 + 클라이언트(`-autoplay chase`), 2라운드: 카운트다운·진행·관전·결과·다음 라운드까지 그림이 바뀌며 진행, 결과 화면에서 승자가 승리 동작, 예외 없음, 핑 17ms. 한 번 더(1라운드) 돌려 공중 사망 웅덩이가 아래 면에 내려앉는 것 확인.
- 첫 번째 접속 시험에서 클라이언트 창이 시작 15초 만에 정상 종료(예외 없음, `-quitAfter` 전) 한 번. 같은 명령으로 두 번 더 돌렸을 때는 재현되지 않았다. Unity 클라이언트 세션 기록에도 같은 증상이 한 번 있다(창 클릭·Enter 추정). 이번 변경과의 관계는 확인 못 함.
- Gemini로 시험을 맡기려 했으나 셸 무제한 실행(`--yolo`)이 안전 검사에 막혀 같은 명령을 직접 돌렸다.

확인 안 함: 에디터 플레이 모드, 사람이 키보드로 직접 해 본 손맛, 넓은 화면 비율, 성능(그림 9장, 캐릭터 시트 각 1536 × 2048 비압축 ≈ 12MB씩, 합계 약 110MB의 텍스처 메모리 — 압축은 화질 확인 후 정할 일).
