# 입력 대기 줄이기

담당 세션: `[OnlineSeverGame] 입력 대기 줄이기 · 01` (맵 선택·칼 판정 · 01이 시작한 하위 세션). 패킷 변경 없음, 프로토콜 v4 그대로.

같은 PC(핑 16~17 ms)에서도 내가 누른 입력이 서버 입력 큐에서 3틱(0.15초)을 기다린 뒤에야 적용되던 것을, 대기 줄이 생겨도 2초 안에 사라지게 고쳤다(서버). 그러면서 드러난 클라이언트 화면 보간 문제(미확인 입력이 0개일 때 몸이 한 스텝 튐)도 고쳤다.

## 1. 어떻게 플레이되는가

- 키를 누르고 서버가 그 입력을 적용하기까지 걸리는 시간이 같은 PC에서 약 0.15~0.2초 → 0.05초 안쪽으로 줄었다. 내 캐릭터는 예전처럼 바로 움직이므로(예측) 손맛은 같고, 달라지는 것은:
  - **위험물 예고가 그만큼 일찍 보인다.** 위험물은 내 예측 시각에 그리므로(맵 선택·칼 판정 작업) 예고가 "미확인 입력 수"만큼 늦게 나타났다. 그 수가 4 → 0~1이 되어, 예고가 약 0.17초(3.5틱) 일찍 보인다(예고 1~1.25초 중 실제로 보이는 시간이 늘어남). 위에서 떨어지는 위험물이 내 몸 기준으로 앞서 그려지는 거리(보간 시각 대비)도 평균 2.9~3.5유닛 → 0.9~1.1유닛.
  - 내가 남을 밀치거나 밟는 일, 상자를 미는 일이 서버에서 더 빨리 일어나 다른 사람 화면에도 그만큼 빨리 보인다.
- 접속 직후·로딩 직후처럼 화면이 잠깐 멈췄다 풀릴 때 대기 줄이 생겨도, 0.55초마다 하나씩 줄어 2초 안에 없어진다(측정: 4개 → 1.7초). 줄이는 틱에는 내 캐릭터가 서버에서 그 틱에 두 스텝을 간다(다른 사람 화면에서 아주 잠깐 빨라 보일 수 있음, 한 번에 한 스텝 0.4유닛 정도). 내 화면에서는 아무 변화가 없다.

## 2. 원인 확인 (숫자)

서버에 플레이어별 입력 큐 기록을 넣었다(`--verbose`면 1초마다, 라운드 끝에는 늘). 비교용으로 예전처럼 하나씩만 꺼내는 `--no-input-trim`을 두고, 같은 실행 파일로 전후를 쟀다.

실행: 서버(포트 7831, `--min-players 4 --seed 5 --maps cycle --exit-after-rounds 4 --verbose --no-input-trim`) + Unity 클라이언트 1(`Client/Build/Windows`, `-autoplay`, 방장, #1) + 봇 3. 같은 PC, 4라운드(4맵 모두).

- 접속 직후 첫 1초(서버 틱 104~120): 클라이언트 입력 13개 도착, 그중 한 번은 **여러 개가 한꺼번에**(bursts 1), 입력이 없어 마지막 버튼을 반복한 틱 7개. 클라이언트가 접속 직후 프레임이 멈췄다가 밀린 틱을 한꺼번에 보낸 것(`NetworkSession`의 `MaxCatchUpTicks` 따라잡기).
- 그 뒤로 클라이언트 큐는 **4라운드 내내 334초 동안 매초 정확히 3**이었다(최소도 3). 그 뒤로는 한꺼번에 오는 일도, 빈 틱도 0번. 서버는 틱마다 하나만 꺼내므로 한 번 생긴 줄이 다시 줄지 않는다.
- 봇 3개(프레임 멈춤 없음)는 내내 0.
- 클라이언트 로그 `pending`(미확인 입력 수, 5초마다): 3이 23번, 4가 26번. = 큐 3 + 보낸 뒤 서버 틱을 기다리는 0~1개.
- 위험물을 그리는 시각이 보간 시각보다 앞서는 정도(`hitview lead`): 4.94~5.13틱 = 미확인 입력(약 3~4) + 보간 2틱 − 1.

결론: 원인은 브리프의 추정대로 "따라잡기로 몇 틱이 한꺼번에 오면 큐가 늘고, 하나씩만 꺼내니 영영 줄지 않음"이다. 서버 틱이 늦어 건너뛴 경우(`TickTimer`는 늦은 틱을 다시 돌리지 않고 건너뜀)도 같은 식으로 줄을 늘린다(이번 실행에서는 건너뛴 틱 없음). 맵 선택·칼 판정 작업에서 본 4~5는 그때 생긴 줄이 4였던 것.

## 3. 어떻게 고쳤는가

### 규칙 (서버, `Server/GameServer/InputBacklog.cs`, `GameRoom.StepWorld`)

- 틱마다 그 플레이어 입력을 꺼낸 뒤 **큐에 남은 수**를 본다.
- 10틱(0.5초) 동안 남은 수가 한 번도 0이 아니었으면(= 늘 1개 이상 여유가 있었음), **다음 틱 하나에서 입력 두 개를 꺼내 차례로 적용**한다(`PlayerPhysics.Step` 두 번). 그 틱 다음부터 다시 10틱을 잰다. 그래서 줄은 최대 11틱에 하나씩 준다.
- 남은 수가 한 번이라도 0이었으면 아무것도 안 한다.
- **틱 경계 흔들림 대비(창 늘리기)**: 입력이 서버 틱 바로 앞뒤로 도착하면(어느 틱엔 0개, 다음 틱엔 2개) 남은 1개는 밀린 줄이 아니라 흔들림을 받아 주는 여유다. 처음 규칙(창 10틱 고정)으로 돌렸을 때 그런 상태가 된 봇 3개에서 **따라잡기 직후 큐가 빈 틱이 따라잡기 수와 똑같이** 나왔다(라운드마다 따라잡기 7/10/15/20번 = 빈 틱 7/10/15/20번). 빈 틱에는 서버가 마지막 버튼을 반복하므로, 사람 클라이언트라면 그때 버튼이 바뀌었을 경우 보정이 생긴다.
  - 그래서 따라잡은 뒤 한 창 안에 큐가 빈 틱이 나오면 **창을 두 배로**(10 → 20 → 40 → 80 → 160틱, 최대 8초), 빈 틱 없이 한 창이 지나면 **절반으로**(최소 10틱) 한다. 진짜 밀린 줄은 따라잡아도 빈 틱이 안 생기므로 계속 10틱마다 빠르게 줄고, 흔들림 여유는 거의 건드리지 않는다.
  - 시험(같은 흐름, 8틱에 한 번 입력이 한 틱 늦게 옴, 1200틱): 창 고정이면 따라잡기 20번·빈 틱 20번, 창 늘리기면 그 4분의 1 이하.
- 예전 규칙은 그대로: 8개 넘게 쌓이면 오래된 것부터 버림, 큐가 비면 마지막 버튼 반복.

### 왜 버리지 않고 두 개를 적용하나

- 브리프의 예시는 "남은 줄을 덜어 내고(버리고) 처리한 것으로 친다"였다. 버리면:
  - 그 입력에 든 점프·대시 **눌림이 사라질 수 있고**,
  - 클라이언트는 그 입력으로 한 스텝을 예측했는데 서버는 안 갔으므로 **매번 한 스텝(최대 0.4유닛, 대시 중이면 더) 보정**이 생긴다.
- 두 개를 모두 적용하면 서버도 입력마다 한 스텝씩 가므로 클라이언트 예측(입력 하나 = 한 스텝)과 그대로 맞는다. 보정이 생기지 않고 눌림도 지켜진다. 다른 플레이어·위험물은 그 틱에 한 번 처리되므로, 그 틱에 내가 두 스텝 가는 것만 다르다.
- 악용: 줄이 0.5초 내내 1개 이상일 때만, 11틱에 한 번만 한다. 일부러 입력을 많이 보내도 최대 약 9% 더 빠를 뿐이고, 그만큼 입력을 미리 보내야 하므로 이득이 없다.

### 클라이언트 (`Client/Assets/Scripts/Game/NetworkSession.cs`)

- 입력 보내기는 바꾸지 않았다. 따라잡기(`MaxCatchUpTicks`)를 없애면 멈춘 동안 서버가 마지막 버튼을 반복해 예측이 어긋나므로, 클라이언트는 지금처럼 보내고 서버가 줄을 정리하는 쪽이 낫다. 네트워크가 잠깐 막혔다가 몰려 오는 경우도 서버 쪽 규칙 하나로 함께 처리된다.
- **보정(`Reconcile`)에서 화면 보간 시작점 지키기**: 서버만 고치고 예전 클라이언트로 돌리자 `[Net] correction 0.3~0.44u` 줄이 983번, 예측 어긋남(mispredicts) 124 → 1883번이 됐다. 모두 `pending=0`(다시 굴릴 입력 없음)일 때였다.
  - 원인: 내 몸은 직전 예측 스텝의 시작(`_predictedPrev`)과 끝(`_predicted`) 사이를 틱 안 시간으로 보간해 그린다. 스냅샷을 받아 다시 굴릴 입력이 0개면 예전 코드는 시작점도 스냅샷 상태로 덮어서, 틱 중간에 그리던 몸이 틱 끝으로 한 스텝(0.3~0.44유닛) 튀었다(보정 오프셋이 부드럽게 메워 주긴 함). 예전에는 미확인 입력이 늘 3개 넘게 남아 이 경우가 거의 없었다.
  - 고침: 다시 굴릴 입력이 없으면 시작점은 그대로 두고 끝점만 서버 상태로 바꾼다. 서버가 예측과 같은 결과면 화면 위치가 전혀 안 바뀐다. 결과: 보정 줄 0번, 어긋남 4번(최대 0.17유닛, 밟기 등 서버만 아는 일).

### 설정과 기록

- `RoomConfig.TrimInputQueue`(기본 켬), `InputTrimWindowTicks`(10), `InputTrimMaxWindowTicks`(160), `InputQueueSlack`(0 = "남은 수가 늘 0보다 크면").
- 서버 옵션 `--no-input-trim`: 예전처럼 하나씩만(전후 비교용).
- 라운드 끝 로그(늘): `inputs: #1 queue avg 0.05 max 1, catch-up 2, empty 0, bursts 0 (max 1 at once), dropped 0; #2 …`
  - queue = 틱마다 꺼낸 뒤 남은 수, catch-up = 두 개 적용한 틱, empty = 큐가 비어 반복한 틱, bursts = 틱 사이에 2개 넘게 도착한 횟수, dropped = 8개 넘쳐 버린 수.
- `--verbose`: 1초마다 `inputs tick N: #1 q 0 (min 0 max 1) in 20 bursts 0 empty 0 catch-up 0, …`, 따라잡은 틱마다 `input #1 tick N caught up (2 inputs, K still queued, window W)`.
- 프로토콜 문서 8장 '서버'와 5장 '한 틱의 처리 순서'에 규칙을 적었다.

## 4. 전후 비교

같은 실행 파일, 같은 조건: 서버(`--min-players 4 --seed 5 --maps cycle --exit-after-rounds 4 --verbose`) + Unity 클라이언트 1(`-autoplay`, #1) + 봇 3, 같은 PC, 4라운드(4맵). 포트 7831~7834.

| | 전 (`--no-input-trim`, 예전 클라이언트) | 서버만 고침 (예전 클라이언트) | 서버 + 클라이언트 고침 (최종) |
|---|---|---|---|
| 클라이언트(#1) 서버 큐, 매초 기록 | **3** (334번 모두) | 0 (266번), 접속 직후 4·2 | **0** (338번), 접속 직후 4·2 |
| 라운드별 큐 평균 (1~4라운드) | 3.00 / 3.00 / 3.00 / 3.00 | 0.08 / 0 / 0 / 0 | 0.05 / 0 / 0 / 0 |
| 접속 직후 줄 없애기 | 없음(끝까지 3) | 4번 따라잡아 1.7초 만에 0 | 4번 따라잡아 1.7초 만에 0(틱 122~155) |
| 클라이언트 `pending`(살아 있을 때, 5초마다) | **4** (26번 모두) | 1 (27번 모두) | **0** 24번, **1** 7번 |
| 위험물 그리는 시각 앞섬(`hitview lead`) | 4.94~5.13틱 | 1.44~1.67틱 | 1.43~1.65틱 |
| 떨어지는 위험물 위치 차(예측 vs 보간) 평균 | 2.94~3.54유닛 | 0.83~1.17유닛 | 0.87~1.13유닛 |
| 클라이언트 보정 줄(0.3유닛 넘음) / 어긋남 수 / 최대 | 23 / 124 / 1.61유닛 | **983 / 1883** / 1.12유닛 | **0 / 4 / 0.17유닛** |
| 봇 3개 큐 평균 | 0 | 0 | 0 |
| 클라이언트 예외 | 0 | 0 | 0 |

- `pending`은 '보냈지만 아직 서버 확인을 못 받은 입력 수'. 같은 PC에서 이상적인 값은 0~1(보낸 입력이 다음 서버 틱에 적용되고 스냅샷이 곧 돌아옴). 목표(1~2 이하) 달성.
- 서버 큐 대기 3틱 = 입력마다 0.15초 더 늦게 적용되던 것. 이제 0.
- 표에 없는 중간 실행(after2: 창 10틱 고정 + 고친 클라이언트, 포트 7833)에서 봇 3개가 틱 경계에 걸려 큐 평균 0.79~0.82, 라운드마다 따라잡기 = 빈 틱(7/10/15/20번)이 나왔다. 이것을 보고 창 늘리기를 넣었다(3장). 그 실행의 클라이언트 숫자는 최종과 같았다(큐 0, `pending` 1, 보정 줄 0, 어긋남 0). 봇이 경계에 걸리느냐는 실행마다 운이라 최종 실행에서는 안 걸렸다.
- 창 늘리기를 넣은 뒤 봇만으로 따로 확인: 서버 3개(포트 7835~7837) × 봇 8 × 2라운드 = 48 플레이어·라운드. 7836·7837은 봇이 틱 경계에 딱 걸린 경우(라운드당 2개씩 도착 4023·5115번, 큐 평균 0.27·0.30)인데 **따라잡기 0번**, 빈 틱은 서버마다 7번(흔들림 자체로 생긴 것). 7835는 따라잡기 3번·빈 틱 3번(따라잡은 뒤 빈 틱 → 창이 두 배가 됨). 창 고정일 때(봇 하나가 라운드마다 7~20번)와 비교.
- 원본 로그: `side-session-notes/local_b7d56d9a-.../input-latency-01/logs/` (`server-before.log`, `client-before.log`, `*-after.log`, `*-after2.log`(창 고정, 고친 클라이언트), `*-after3.log`(최종)).

## 5. 직접 돌려 보기

```
dotnet run --project Server/GameServer -- --port 7840 --min-players 4 --verbose
dotnet run --project Tools/BotClient -- --port 7840 --count 3
Client/Build/Windows/Client.exe -server 127.0.0.1:7840 -autoconnect -autoplay
```

- 서버 창의 `inputs tick … #1 q …`(1초마다)에서 클라이언트(#1) 큐가 접속 직후 잠깐 1~3이었다가 `caught up` 몇 번 뒤 0~1로 내려가는지 본다. 라운드 끝 `inputs:` 줄의 `queue avg`.
- 클라이언트 로그(`%USERPROFILE%/AppData/LocalLow/OnlineSeverGame/OnlineSeverGame/Player.log`)의 `[Net] stats … pending=`. 죽어 관전 중일 때는 보정을 안 하므로 64까지 찬다(원래 그렇다, 무시).
- 비교: 서버에 `--no-input-trim`을 붙이면 예전처럼 줄이 그대로 남는다.

## 6. 확인한 것과 남은 일

### 실제로 확인한 것
